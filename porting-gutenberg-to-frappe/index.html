Porting Gutenberg to Frappe

July 26, 2026

lakshyajeet

Building content-heavy web pages inside the Frappe Framework has relied on a familiar, battle-tested pipeline: a standard Web Page DocType, a Rich Text editor or serial page builder, and a Jinja template to render it to the end user. It works. It has powered thousands of ERPNext sites, documentation portals, and marketing pages. While it works, having used WordPress’s block editor, Frappe’s default editor feels too basic.

Like most of my projects, this one also started with a “What if…?”: what if we could have WordPress Block Editor’s editing experience inside Frappe?

I am well aware that Frappe Builder exists to solve exactly this problem. However, my motivation was two-fold: first, it was a fascinating technical challenge that gave me the experience to embed Gutenberg portably into almost any environment. Second, I wanted to achieve a specific balance, a lightweight, “editor-first” experience that remains feature-rich without the overhead of a full-scale site builder.

In this article, we will explore the mechanics of injecting a modern React-based editor into Frappe’s hybrid jQuery and Vue-driven UI, serializing block-delimited markup into MariaDB, and dynamically generating CSS via modern Vite asset pipelines.

Rethinking How We Build Content

For basic, text-heavy content like blog posts or standard “About Us” pages, the legacy WYSIWYG (What You See Is What You Get) approach works perfectly, It’s a familiar and low-friction way that doesn’t require complex state management or heavy client side JS to function.

However, as the requirements shift towards more complex pages like interactive landing pages, or documentation the limitation of traditional editor becomes difficult to work with and maintain.

  • The “Span Soup” Problem: Traditional editors lack structural awareness, when a user tried to build a complex layout with multiple interactive elements, they often end up fighting each other. This inevitably leads to “span soup”- deeply nested tags, forced styles and redundant content so that it does not break responsive design on mobile.
  • Performance and Editing Constraints: As pages grow more complex, it becomes difficult to manage and edit them, especially when we add more elements: complex layouts, interactive components, or nested containers, the editing experience becomes increasingly sluggish.

On a personal level, I just genuinely appreciate the Gutenberg component ecosystem, so why not use it? The WordPress block editor provides a beautiful, drag-and-drop authoring experience that content creators already know and love. I wanted that exact user experience, but backed by Frappe’s Python based backend.

Why WordPress Gutenberg in Frappe?

When looking to replace the legacy editor, the obvious alternative usually is to build a custom editor on our own, and as mentioned previously that is exactly what Frappe Builder has done.

So why did I choose to import @wordpress/block-editor into a non-WordPress, Python environment?

This is not a silver bullet, and bringing massive WordPress NPM packages into Frappe carries bundle-size overhead with it, but the architectural tradeoffs are actually quite favorable:

  • Zero-cost Abstractions (The Data Model): Gutenberg elegantly stores the block structures as standard HTML with annotated JSON comments (<!-- wp:paragraph {"align":"center"} --> <p>Text</p> <!-- /wp:paragraph -->). This means Frappe doesn’t need any complex relational schema or dedicated block table to store page data. It can store the entire AST (Abstract Syntax Tree) as a single Long Text string, and Gutenberg parses it back into a React state tree effortlessly.
  • The Component Ecosystem: By utilizing @wordpress/block-library, we instantly inherit dozens of highly tested, accessible, and responsive blocks (Code snippets, Tables, Columns, Audio, Video) without writing a single line of UI code ourselves. If someday we want to add our own block it is a very straightforward process as building a block in WordPress is quite easy and very highly documented.
  • Memory Safety & State Management: Gutenberg leverages highly optimized React data stores (@wordpress/data, built heavily on Redux principles), ensuring that even pages with thousands of nested blocks won’t crash the browser’s main thread. It handles focus management, history tracking (undo/redo), and deeply nested block state with incredible efficiency.

 Intercepting the Workflow: The Architecture

The main obstacle in integrating a React-based block editor into Frappe is the fundamental environment mismatch. WordPress Block Editor expects to talk to a PHP backend via the WP REST API. It expects WordPress global variables. Frappe, on the other hand, expects a Vue.js based frontend with a Python based backend.

So we basically want to “hijack” the standard Frappe DocType rendering cycle and inject a React root over the existing DOM.

To build this bridge, we intercept the standard “Web Page” DocType in Frappe using a client script (block_editor_web_page.js). Add a custom “Block Editor” option to the content type, create a custom DOM node, and mount our React application as an overlay to it and create few custom fields to store our content data in the backend.

// block_editor_frappe/public/js/block_editor_web_page.js

let editor_node = null;
let editor_manager = null;

frappe.ui.form.on("Web Page", {
    setup_editor: function (frm) {
        // We check if the Vite-compiled React bundle has successfully attached 
        // the mount function to the global window object. If not, the script fails gracefully
        // and falls back to standard Frappe rendering.
        if (!window.mountDMBlockEditor) {
            console.error("Block Editor React bundle is missing.");
            return;
        }

        // We utilize the Frappe form lifecycle to mount our React app.
        // We isolate the React DOM tree inside a dedicated 'editor_node' to prevent 
        // Frappe's global jQuery logic from accidentally mutating React's virtual DOM.
        if (!editor_manager) {
            editor_manager = window.mountDMBlockEditor(
                editor_node,
                {
                    // Pass Frappe's current DB state down into React as props.
                    // React treats Frappe's database as the single source of truth upon initialization.
                    title: frm.get_title() || "",
                    content: frm.doc.block_editor_html_internal || "",
                    route: frm.doc.route || "",
                    published: frm.doc.published || 0,
                    meta_title: frm.doc.meta_title || "",
                    meta_description: frm.doc.meta_description || "",
                },
                // The 'onChange' callback. Every time React's state changes (keystrokes), 
                // we push the serialized string back into Frappe's internal DocType state.
                // This ensures Frappe's native "Save" button still works perfectly if the user clicks it.
                (raw_content) => {
                    frm.set_value("block_editor_html_internal", raw_content);
                },
                // The 'onClose' callback hides the React overlay, returning the user to the Desk.
                () => {
                    editor_node.style.display = "none";
                },
                // The 'onSave' callback. When the user clicks the blue 'Save' button *inside* React, 
                // we push all final metadata up to the Frappe form and trigger a backend save.
                (title, rendered_content, route, published, meta_title, meta_description) => {
                    frm.set_value("title", title);
                    frm.set_value("block_editor_html_rendered", rendered_content);
                    frm.set_value("route", route);
                    frm.set_value("published", published);
                    frm.set_value("meta_title", meta_title);
                    frm.set_value("meta_description", meta_description);
                    frm.save();
                },
                frm.doc.name,
            );
        } else {
            // If the React app is already mounted in memory, we don't remount. 
            // We just trigger an update method to push new Frappe data down the tree.
            editor_manager.update(frm.doc.block_editor_html_internal || "", frm.doc.name);
        }
    }
});

The Legacy Stack Fallback: Notice how we manage the content_type toggle in the codebase. If the user switches the content_type dropdown back to “HTML” or “Markdown”, the script automatically unmounts the React node and restores Frappe’s standard editor options. This ensures backwards compatibility for older pages that were not built using blocks.

Deep Dive into Serialization

This is where the heavy lifting happens. Once React is mounted, the Gutenberg engine needs to parse Frappe’s raw database string back into a living React AST (Abstract Syntax Tree), allow the user to edit it in a visual canvas, and then serialize it back out.

To do this effectively and securely, we maintain two distinct, hidden fields in the Frappe Web Page database schema:

  1. block_editor_html_internal (Source of Truth): Contains the WordPress block grammar (HTML annotated with JSON comments). This is used strictly to re-hydrate the React editor. It is never shown to the public.
  2. block_editor_html_rendered (Production Output): Contains pure, sanitized, static HTML with all CSS utility classes applied. This is what the Frappe Jinja template serves to public visitors.
// block_editor_frontend/src/BlockEditor.tsx

import { parse, serialize, getSaveContent, type BlockInstance } from "@wordpress/blocks";
import { BlockEditorProvider, BlockList, WritingFlow } from "@wordpress/block-editor";
import { createElement, RawHTML, useState, useRef } from "@wordpress/element";

export function BlockEditor({ value, onChange, onSave }: BlockEditorProps) {
  
  // We lazily initialize the parser only once on component mount. 
  // 'value' is the raw string from Frappe's DB (e.g., <!-- wp:paragraph --><p>Hi</p><!-- /wp:paragraph -->). 
  // parse() tokenizes this massive string and converts it into a structured array of React BlockInstances.
  const [blocks, setBlocks] = useState<BlockInstance[]>(() => {
    initEditor();
    return parse(value) ||[];
  });

  // Every time the user types a letter or drags a block, this function fires.
  // We serialize the AST back to a WP-commented string and send it to the Frappe JS Bridge.
  const handleInput = (newBlocks: BlockInstance[]) => {
    setBlocks(newBlocks);
    
    // Serialization overhead is mitigated by React's batched state updates.
    const serializedContent = serialize(newBlocks);
    setIsDirty(serializedContent !== lastSavedRef.current);
    
    onChange?.(serializedContent);
  };

  // When the user hits 'Save', we must generate the final, clean HTML for the public website.
  // We recursively map over the AST. For each block, we map Gutenberg attributes
  // into actual frontend CSS classes.
  const getRenderedHTML = (blocks: BlockInstance[]): string => {
    const renderBlocks = (blocks: BlockInstance[]): string => {
      return blocks.map((block) => {
        // Extract attributes and inject dynamic layout classes (e.g., is-layout-flex)
        const attributes = {
          ...block.attributes,
          className: getBlockContextualClasses(block.name, block.attributes),
        };
        
        const innerHtmlString = block.innerBlocks.length > 0 ? renderBlocks(block.innerBlocks) : "";
        
        // `getSaveContent` executes the block's specific save() React function, 
        // stripping away WP comments and returning pure, production-ready HTML.
        return getSaveContent(
          block.name,
          attributes,
          createElement(RawHTML, { children: innerHtmlString }) as any
        );
      }).join("");
    };

    return renderBlocks(blocks);
  };

  // ... (UI Render Logic Omitted for Brevity)
}

Data enters as a raw string from Frappe, gets tokenized by @wordpress/blocks, is manipulated by the user inside the <BlockList /> canvas, and exits via our custom recursive getRenderedHTML function. This architectural pattern cleanly separates the editor’s internal state concerns from the public output, ensuring that the frontend website only ever renders clean HTML, requiring zero JavaScript on the client side to display the page.

The Build Pipeline / Orchestration

Combining a Python/Jinja backend with a modern React/TypeScript frontend requires careful orchestration. We cannot simply run a Node.js development server in production; the React application must be compiled into static assets that Frappe’s bench CLI can serve via Nginx or Werkzeug.

We achieve this via Vite, compiling the React application into distinct bundles placed directly into Frappe’s standard /public directory.

Furthermore, we solved a massive design problem during this build phase: How do we ensure the editor’s visual styles (colors, spacing, typography) perfectly match the public website’s styles without writing duplicate CSS?

In a standard WordPress environment, this is handled by theme.json. Because we don’t have WordPress, we created a single source of truth (editorSettings.ts) and built a highly custom Vite Virtual Module plugin to dynamically generate CSS at build time.

// block_editor_frontend/vite.config.ts

import { defineConfig, type Plugin } from "vite";
import { generateThemeCss } from "./src/utils/generateThemeCss";

// Vite plugins allow us to intercept imports at compile time. 
// We create a "virtual" module that doesn't actually exist on the hard drive. 
function virtualWpThemePlugin(): Plugin {
  const virtualModuleId = "virtual:wp-theme.css";
  const resolvedVirtualModuleId = "\0" + virtualModuleId;

  return {
    name: "vite-plugin-wp-theme-generator",
    resolveId(id) {
      // If the code requests our virtual CSS file, intercept the resolution.
      if (id === virtualModuleId) return resolvedVirtualModuleId;
    },
    load(id) {
      // When the React app imports "virtual:wp-theme.css", Vite triggers this load function.
      // We parse the JSON editorSettings and dynamically generate thousands of lines 
      // of CSS variables (--wp--preset--color) and utility classes (.has-black-color) in memory.
      if (id === resolvedVirtualModuleId) {
        return generateThemeCss();
      }
    },
  };
}

export default defineConfig(({ mode }) => {
  const isFrontend = process.env.BUILD_TARGET === "frontend";

  return {
    plugins:[
      virtualWpThemePlugin(), 
      react(),
      babel({ plugins: [["babel-plugin-react-compiler", { target: "18" }]] })
    ],
    build: {
      // We output the compiled React application directly into Frappe's app asset folder.
      // This allows Frappe's native web server to serve the JS/CSS without a separate Node instance.
      outDir: "../block_editor_frappe/public/vite",
      emptyOutDir: false,
      cssCodeSplit: false,
      rollupOptions: {
        input: isFrontend
          ? resolve(__dirname, "src/scripts/frontendStyles.ts")
          : resolve(__dirname, "src/main.tsx"),
        output: {
          // Predictable file naming ensures our Frappe Python backend 
          // can easily link these exact assets in the Jinja templates without needing complex manifest lookups.
          entryFileNames: isFrontend ? "js/block_editor_frontend.js" : "js/block_editor_main.js",
          assetFileNames: isFrontend ? "css/block_editor_frontend.css" : "css/block_editor_main.css",
        },
      },
    },
  };
});

To tie it all together natively, we leverage Frappe’s after_install hook in hooks.py to automatically trigger an npm install and npm run build via Python’s subprocess module.

Code quality is strictly enforced across the language chasm: ruff lints the Python logic, while eslint and prettier ensure the React codebase remains pristine, all bound together by a unified .pre-commit-config.yaml.

State Management: Passing Data Across the Stack

The “distributed state problem” is the bane of modern hybrid architectures. How do we get the DocType state from a MariaDB row, pass it through a Python controller, feed it into a legacy jQuery client script, and safely inject it into an isolated React context all while ensuring data remains strictly typed?

We solve this using a unidirectional data flow governed by a global window registry acting as an API boundary.

// block_editor_frontend/src/main.tsx

// We declare a global TypeScript interface. This creates a strict contract 
// so the legacy jQuery application (Frappe Desk) knows exactly what data shapes 
// it must provide to instantiate the React application.
declare global {
  interface Window {
    mountDMBlockEditor: (
      element: HTMLElement,
      props: {
        content: string;
        title: string;
        route: string;
        published: number;
        meta_title: string;
        meta_description: string;
      },
      onChange: (content: string) => void,
      onClose: () => void,
      onSave: (title: string, rendered: string, route: string, published: number, meta_title: string, meta_description: string) => void,
      docName: string,
    ) => void;
  }
}

let root: Root | null = null;

window.mountDMBlockEditor = (element, props, onChange, onClose, onSave, docName) => {
  if (!root) {
    root = createRoot(element); // Initialize the React 18 Root
  }

  // We destructure the database state passed from Frappe and inject it 
  // directly into the React BlockEditor as props. React now "owns" the UI state.
  const { content, title, route, published, meta_title, meta_description } = props;

  const render = (newContent: string, newDocName: string) => {
    root?.render(
      <StrictMode>
        <BlockEditor
          key={newDocName} // Changing the key forces a full React remount if the Frappe doc changes
          value={newContent}
          title={title}
          route={route}
          published={published}
          meta_title={meta_title}
          meta_description={meta_description}
          onChange={onChange}
          onClose={onClose}
          onSave={onSave}
        />
      </StrictMode>,
    );
  };

  render(content, docName);

  // We return an API object back to the Frappe JS script.
  // This allows Frappe to programmatically update the React state if the database 
  // changes via background events, or destroy the React instance entirely to free memory.
  return {
    update: render,
    unmount: () => {
      root?.unmount();
      root = null;
    },
  };
};

This unidirectional setup eliminates race conditions. React completely owns the UI state and memory lifecycle, but Frappe remains the single source of truth for the persistent data.

To serve this to the end user, we utilize Frappe’s Python override hooks. The backend implementation is intentionally minimal, acting only as a data router:

# block_editor_frappe/overrides/web_page.py

from frappe.website.doctype.web_page.web_page import WebPage

class BlockEditorWebPage(WebPage):
    def get_context(self, context):
        super().get_context(context)

        # If the user didn't select "Block Editor", we fall back to standard Frappe rendering.
        if self.content_type != "Block Editor":
            return

        # Inject the pure, rendered HTML into the Jinja context.
        # This completely bypasses the need for the frontend to run React to see the page.
        context.block_editor_content = self.block_editor_html_rendered or ""

        # Point the renderer to our custom Jinja template that includes our Vite CSS assets.
        context.template = "block_editor_frappe/templates/pages/web_page_block_editor.html"

The simplicity of this Python class is the entire point: the React frontend does all the heavy analytical lifting and serialization, and the backend simply serves the resulting static string at light speed.

Limitations and Future Enhancements

While I am extemely content with this implementation, but we must be honest about its current constraints. Mashing two massive ecosystems together results in inevitable friction points:

  1. WordPress API Reliance: Some native Gutenberg blocks (like dynamic Post Grids, Navigation Menus, or Search) attempt to fetch data dynamically via WordPress REST API endpoints (/wp-json/). Because Frappe doesn’t possess these specific endpoints, those complex dynamic blocks currently fail to render and must be filtered out of the block registry.
  2. Asset Management Disconnect: Currently, dragging and dropping an image into the editor embeds it as a Base64 string or relies on external URLs. It completely bypasses Frappe’s native File Manager DocType. This means images uploaded via the editor don’t show up in the standard Frappe file list, breaking centralized asset management and potentially inflating the database size.
  3. Environment Bypasses: If a user edits the block_editor_html_internal string directly via a Python script or the Frappe REST API (bypassing the React UI), the block_editor_html_rendered field will not update automatically, causing a synchronization mismatch between the database and the public website.

Where do we go from here?

  • Frappe Native Block API Middleware: We can build a custom Python/JS middleware layer that intercepts Gutenberg’s outgoing WP REST API calls and maps them to Frappe DocType queries. This would allow a native block to dynamically fetch ERPNext data (e.g., embedding a live, filtered grid of Item DocTypes directly into a Web Page layout). Instead we can also simply create new blocks for our usecase which do not even depend on WordPress APIs and used Frappe’s API natively.
  • Media Upload Bridging: We can also add custom React hook that intercepts the block editor’s image drop event, reroutes the file to Frappe’s upload_file endpoint, and returns the generated Frappe File URL back to the image block, perfectly synchronizing the two systems. Maybe we can have a Media Library modal equivalent here.
  • Code-editor Mode: Like in WordPress, adding a code editor mode here will be or very helpful for debugging and checking the exact markup generated by the editor.

Conclusion

Porting the WordPress Gutenberg editor into the Frappe Framework was more than just a pursuit of a “prettier” UI; it was a deep dive into reconciling two fundamentally different architectural philosophies. By successfully embedding a React-based, state-driven editor into Frappe’s jQuery and Vue-driven ecosystem, this project proves that we don’t have to choose between the robustness of a Python backend and the world-class authoring experience of modern JavaScript libraries.

While challenges remain, specifically regarding the alignment of asset management and the “hijacking” of WordPress-specific API calls, the foundation is solid. This integration opens the door for a new class of Frappe-powered websites: those that demand the technical rigor of an ERP and the aesthetic flexibility of a modern CMS.

Ultimately, this project demonstrates that with the right orchestration of build tools and state management, we can bypass the limitations of a “basic” editor and provide content creators with a truly professional, block-first experience without leaving the Frappe ecosystem.
